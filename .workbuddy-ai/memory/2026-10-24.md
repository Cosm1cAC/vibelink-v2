## magpie 网关 workbuddy 供应商排查

结论：WorkBuddy AI（workbuddy-ai，OAuth 账号 cosm1cac，Pro）本身没坏，是 magpie 路由组的「首字超时 30s」把慢首字请求掐死了。

关键事实：
- magpie 配置目录 `~/.config/magpie`（providers.json / settings.json / routing/*.jsonl / usage.jsonl），程序 `%LOCALAPPDATA%\Programs\magpie\magpie.exe`，网关 127.0.0.1:3425。
- 路由组 `auto-deepseek-v4-1-flash` 的 `firstToken: 30`（可选 0=一直等 / 30 / 60 / 120，UI 在「路由 → 组卡片 → 编辑」）。
- workbuddy-ai 首字实测：deepseek-v4.1-flash p50 20.4s、flash-sg p50 20.7s、step-5-preview p50 57.9s（dsh 上下文 p50 ≈ 100K token）。30s 内出字属运气，超时即 504 `no first token in 30s`。
- 同组兜底成员当时全废：opencode-zen 免费额度 429、commandcode2 周额度 429（10-30 恢复）→ 一旦 workbuddy-ai 超时整条路由失败。
- WorkBuddy 桌面端对话正常是因为客户端没有 30s 首字上限，同样的慢只是它愿意等。
- 另一个供应商 `workbuddy-api`（自定义 Key，chat https://www.workbuddy.ai/v2）「测试」必挂：上游只支持流式（400 `Non-stream chat request is currently not supported`），且首条消息必须是 system（400 `first message is not system prompt`）。流式+system 首条时正常，首字 1.5–3.8s，比 OAuth 那条快一个数量级。

修复建议：把组首字改 2 分钟/一直等；或把 workbuddy-api 放进组成员靠前位置（客户端需流式 + system 首条）；并补一个真正有余量的兜底成员。

### 补充（14:57）：WorkBuddy API 三个模型全红点是误报

- 供应商页「N 个模型中有 N 个没有响应」来自 magpie 的逐模型探活，请求体写死在二进制里：
  `{"model":%q,"messages":[{"role":"user","content":"hi"}],"max_tokens":16}` —— 无 `stream`、无 system 首条，正好踩中 WorkBuddy /v2 的两条硬约束，必然 400。所以自定义 Key 的 workbuddy-api 永远变不绿，且 provider 配置/CLI 都没有强制流式的开关（`magpie group set` 也不认 firstToken，只能在 UI 改）。
- 实测三个模型（14:58）：非流式全 400；流式 + system 首条全部 200，首字 deepseek-v4.1-flash 1.57s / glm-5.3-flash 3.06s / kimi-k2.6 1.48s。
- 仅 user 消息时：workbuddy-ai（插件）自动补 system 能过；workbuddy-api 报 `first message is not system prompt`。所以自定义 Key 那条只适合会发 system 首条的客户端（opencode/dsh 会）。
- 不要点「取消选中没有响应的模型」，会把可用的模型从 Agent 列表摘掉。
